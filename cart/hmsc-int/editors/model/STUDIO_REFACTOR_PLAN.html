Studio.tsx → studio/

A side-by-side decomposition of the 3,915-line Studio modeling viewport. Zero behavior change, zero edits to the existing file, single-line instant swap, single-line instant revert.

The thesis. Nothing about how Studio works changes. We lift the same code, byte-for-byte where it's already separable, into a module that mirrors the UI's own structure (scene · overlays · toolbars · dialogs) and pushes the one true monolith — the 2,680-line StudioViewport — onto a spine of focused hooks. The current Studio.tsx is never touched; it stays frozen as the diff breadcrumb. When the new tree builds and self-shots clean, swapping it in is one import line. If anything looks off, reverting is the same one line.
SAFE pure lift — props-only / stateless, moves verbatim CARE stateful extraction — preserve hook order & keys HOT shared mutable state — the delicate seam

1 · Why this file hurts

Studio.tsx is 3,915 lines / 253 KB, but the weight is lopsided. ~1,500 lines are already-separable leaf material (config, pure helpers, ~16 self-contained dialogs). The remaining ~2,680 lines are a single function, StudioViewport, carrying 42 useState/useHotState + 32 useRef + 18 useEffect, every event handler, and one enormous JSX return. Any change means scrolling a quarter-megabyte file and praying you don't trip an unrelated closure.

2 · Design principles

Mirror the UI, not the code

The file's req_* comment blocks already name the seams: a 3D scene, an overlay layer, two toolbars, a stack of dialogs. The directory is that layout — scene/ overlays/ panels/ dialogs/. Someone editing the tier-2 toolbar opens panels/Toolbar2.tsx, full stop.

State lives in hooks, JSX stays dumb

Each tangle of interrelated state becomes one custom hook (useStudioCamera, useStudioPaint…). The viewport calls them in fixed order and hands the results to presentational panels. The hooks own the how; the panels own the look.

Lift verbatim before you reshape

Leaf components and helpers move with their bodies unchanged — same logic, same closures, just a new home and an import. No "while I'm here" rewrites. Cleverness is how parity breaks.

Old file is the breadcrumb

Per the repo's _old convention, the original Studio.tsx is left frozen and untouched as the ground-truth to git diff against — deleted only after you confirm parity, never speculatively.

5 · The parity contract

These are non-negotiable invariants. If any can't be held, that piece doesn't move until it can.

  • Studio.tsx is never edited. It remains on disk, frozen, as the diff source of truth.
  • Every useHotState / localstore string key stays byte-identical — 'studio:showScale', 'studio:mirrorMask', 'studio:texView', 'studio:smooth', STUDIO_PAINT_KEY, STUDIO_TEXTURE_KEY, SCALE_FIGURE_CART_KEY, the V20 store keys. A changed key silently resets twig/hot state.
  • Hook-call order is fixed. The orchestrator calls the five hooks in a stable sequence every render; each hook calls its own useState/useRef/useEffect in the same order they appear today. React's rules-of-hooks identity is thereby preserved.
  • Effect dependency arrays and execution order are carried over unchanged. No effect is merged, split, or re-ordered relative to its neighbors during the move.
  • Ref identity semantics are preserved — a ref that's created once and shared stays a single ref threaded through hook return values, never duplicated.
  • No prop-shape change to StudioViewport. Its 18-field props object stays identical so StudioEditor wiring is untouched.

6 · The instant swap (and instant revert)

Because the new tree re-exports StudioEditor with an identical signature, cutting over is a one-line edit in the sole consumer — and backing out is the same edit reversed. The two implementations can coexist indefinitely; nothing forces a choice until you're satisfied.

Swap in

// cart/hmsc-int/editors/workbench/model/source.tsx - import { StudioEditor } from '../../model/Studio'; + import { StudioEditor } from '../../model/studio';

Revert (if a self-shot looks wrong)

// flip the one line back — Studio.tsx is still fully intact - import { StudioEditor } from '../../model/studio'; + import { StudioEditor } from '../../model/Studio';
Why not a runtime feature-flag? A build-time import is simpler, leaves zero dead branches in the shipped binary, and the revert is just as fast. A flag only earns its keep if you need both live at once in the same build — we don't.

7 · Execution sequence

Built so that a regression is always bisected to the smallest possible change: leaves first (can't break logic), then one hook at a time with a build between each, then the JSX, then the swap. The consumer import stays on the old file until the very end.

  1. Scaffold + leaf lift. Create studio/, move config.ts, helpers.ts, scene/staging.tsx, all overlays/*, panels/StatCell|NumberField, and every dialogs/* — bodies verbatim. index.tsx re-exports a viewport that still inlines the old StudioViewport body importing these new leaves. ✓ tools/rjit ship hmsc-int → green  ·  git commit "studio/: leaf lift"
  2. Extract the easy hooks. Pull useBackdrops, then useTextureExport, then useStudioCamera — these have the cleanest state boundaries. Build after each one. ✓ ship green after each  ·  commit per hook
  3. Extract useStudioPaint. Paint owns its own refs + the bake interval; moderate coupling to the texture hook (resolved by passing ensureTexture deps in). ✓ ship green  ·  self-shot the paint route  ·  commit
  4. Extract useMeshEdit — the hot seam. Selection + gizmo + the 480-line pointer handlers, receiving camera/paint results as explicit args. Build, then exercise every mesh op (extrude/bevel/loopcut/rig/wheel/flip/glass/detach/solidify). ✓ ship green  ·  self-shot  ·  commit
  5. Split the JSX. Carve scene/StudioScene, panels/Toolbar1, panels/Toolbar2, panels/SizeReadout out of the return. StudioViewport is now the slim orchestrator. ✓ ship green  ·  commit "studio/: presentational split"
  6. Parity pass — old vs new, side by side. Both still build. Self-shot the same routes/states through each and compare. This is where divergence surfaces while the live path is still the old file. ✓ shot diff clean  ·  report PNGs + commands
  7. Flip the swap (one line in source.tsx). New tree goes live. Self-shot the real workbench column-4 viewport. ✓ ship green  ·  self-shot  ·  commit "studio/: cut over"
  8. Hand back for verification. STOP. You drive the live editor. Only on your word does the next step run.
  9. Retire the breadcrumb (your word only). Delete Studio.tsx in its own commit so it's a clean, trivially-revertible delete. Move req_1386/1387 to review. ✓ commit "studio/: retire monolith"

8 · Verification protocol

  • Build: tools/rjit ship hmsc-int must stay green at every checkpoint — never let two or more steps stack before a build.
  • Self-shot (never desktop capture): tools/rjit shot hmsc-int --route <r> --out /tmp/studio-<step>.png, cited by path in each progress note. The app reads back its own frame; nothing touches the user's screen.
  • The matrix to shot: empty boot · a part added · object-mode gizmo drag · face select + extrude · loop-cut popup · paint mode + a stroke · backdrop placed · a dialog open (compile). Each must look identical old↔new.
  • Diff discipline: git diff --stat against the frozen Studio.tsx should show leaf bodies arriving unchanged — large moves, near-zero edits. A leaf that shows real line edits is a smell; investigate before continuing.
Net result. StudioViewport goes from ~2,680 lines to a ~200-line orchestrator; the heaviest single file in the new tree is a hook or a toolbar in the low hundreds. Editing the tier-2 toolbar, the camera, or the paint logic each means opening one focused file — and the path there never required touching, or even understanding, the other three. Behavior is bit-for-bit the same; the swap and the escape hatch are each one line.
